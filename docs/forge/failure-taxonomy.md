# 失效模式分类学 — LLM Agent 团队的 16 种死法与结构解药

> 本文档是 Pulsing Forge 最有含金量的资产：每个失效模式都来自真实运行（手工调试 6 轮 + 50 轮压测 + 100 场景试点战役），每个解药都在工具层实现并经压测验证。
> 核心结论：**提示词管不住的，结构才管得住。**

## 第一类：信件语义失效（pulsing 核心修复）

### 1. 自回声风暴
- **症状**：agent 给自己发非静默信 → 唤醒自己 → 再发 → 20 回合限额被空烧（实测 writer 20 连发）
- **结构解药**：工具层拒绝非静默自发信（错误信息本身教会模型改用 silent）；编排器控制口豁免
- **位置**：`forge-runtime` pulsing_send 工具臂

### 2. 越权收件（misroute 的总病根）
- **症状**：审查店把结论寄给同事/writer；judge 的信被 reply-to-sender 直觉劫持
- **结构解药**：收件白名单 ACL（前缀通配）；广播的越权目标**自动收拢**到白名单内而非报错（报错会引发秒级重试风暴——实测 152 次调用/8 分钟）
- **关键教训**：ACL 必须只对模型调用生效、编排器豁免——曾因 codex 走 attach 通道被整体豁免而形同虚设（"假 ACL"事故）

### 3. 破坏性读取灭失（drain 后信件消失）
- **症状**：judge 被要求群发"你信箱里的底稿"，但 drain 早已消费掉它；writer 被踢"去看打回信"而信已不在
- **结构解药**：**账本即登记处**——闸门从 journal 取信件全文嵌入踢信/裁决表；产品化方向：登记处原语（重要信件机器可重放）
- **三次现身**：底稿灭失、打回信灭失、以及通用的"drain 后引用失效"

### 4. ACK 礼貌乒乓
- **症状**：judge 与审查店互相确认收悉，每跳一次 LLM 调用（实测烧穿整轮预算）
- **结构解药**：审查店→judge 回信**自动转静默**；judge 的唯一唤醒点是机器收齐闸门
- **教训**：与 demo10 原版架构对齐——他们的 judge 进程内建闸门，模型根本没有客套的机会

## 第二类：回合/运行时失效（pulsing 核心修复）

### 5. 未读信回合被合法化
- **症状**：回合既不读信也不发信（codex 秒退纯文字），被"空信箱豁免"原谅，触发信永远无人处理 → 外部踢信循环
- **结构解药**：触发信未读且零发送 → 仓内立即重试（≤2 次），不依赖外部看门狗

### 6. 回合挂起
- **症状**：上游不可达时 codex 挂住而非退出（实测 13 分钟）；智谱流断开
- **结构解药**：900 秒回合收割器 + 重试；stderr 落账（`codex_err` 事件）让死因可见

### 7. stderr 管道黑洞
- **症状**：codex stderr 被 pipe 后从未读取（还有管道缓冲塞满反卡 codex 的隐患）
- **结构解药**：异步读尽 + 落账本

## 第三类：协议角色失效（闸门原语，forge-core）

### 8. 草率收尾（假 REPORT）
- **症状**：judge 20 秒发"REPORT=已完成派单"进度备忘，骗走看门狗弃航
- **结构解药**：**完整回路校验**——REPORT 必须伴随 ≥N 家群发+≥N 家回信才算终局

### 9. 单点收尾
- **症状**：收尾权押在一个 LLM 回合上，模型服务抖动即挂（demo10 原版自认 1/5 悬挂率）
- **结构解药**：**双通道收尾**——裁决表全过后 judge 有 120 秒窗口，超时机器默认合账（如实标注"机器默认收尾"）

### 10. 打回投递失败
- **症状**：judge 把 REJECT 写给自己/错店（实测变体），writer 永远收不到，轮子空转
- **结构解药**：**机器代投**——裁决内容在账，寄给谁是形式；闸门取内容代投

### 11. 群发内容缺失
- **症状**：judge 群发占位符（"```脚本逐字```"字面量）或不带回信指令的畸形群发 → 审查店回复散射
- **结构解药**：群发信**逐字底稿校验**（含脚本特征）+ 失败后机器代发（零参数 fanout 语义——demo10 原版 fanout_task 的正确移植）

### 12. 模型重构轮次失败
- **症状**：混波次信箱里，模型无法分辨哪 8 封回信属于本轮 → "无法裁定"
- **结构解药**：**机器裁决表**——闸门从账本按波次解析每店结论，塞进 ARBIT 信；judge 从"磨几分钟自创格式"变"6 秒照表执行"

## 第四类：任务设计失效（场景层）

### 13. 任务可单人完成 → 测不了协作
- **症状**：中继链场景，模型把五道工序自己全干了（物理上它看得见全部信息）
- **解药**：**每节点持密**——工序藏在各自密信里，代劳在信息上不可能；场景设计原则：要测协作，任务必须不可单人完成

### 14. 前缀纪律漂移
- **症状**：CLEAN=/NEEDS_FIX= 被写成 REVIEW_XXX_RESULT/STATUS=BLOCK 等自由格式（8/8 全漂移过）
- **解药**：按**路由**分类而非前缀（judge→审查店=群审、审查店→judge=回信）；内容判定用关键词表

### 15. 基础设施连环坑（运维层，但会伪装成产品 bug）
- **症状清单**：pkill 模式自匹配（外层 shell / os.system 内层 shell / 启动脚本三连咬）、孤儿 codex 跨场景注信、代理阵亡致全线假失败、日志截断竞态、WSL 重启清场
- **解药**：模式与执行者命令行永不共形（`[x]` 字符类原则）；跨场景结算窗+空账本校验；基础设施保姆进程；状态放持久盘
- **教训**：100 场景试点 7 个 bug 全在此层——**测试工装比被测系统脆弱得多**，工装本身需要工程化

### 16. 扇入风暴（30 店广播实证）
- **症状**：高扇入收集者（chief 收 30 家回声）信箱逐封进信，调度器每见新信即触发一回合 → 回合预算与配额被风暴烧穿；同时"收齐→ARBIT"回调对每封迟到回声再触发，单场注入 36 封 ARBIT，收尾 REPORT 永远轮不到
- **解药**（两层，缺一不可）：
  1. **编排器回调幂等**：闸门注入前查账本，已注入过 ARBIT 不再注入（`on_letter` 以 ctx.letters 为幂等键）
  2. **调度器去抖**：检测到新信后等信流静默 2 秒（500ms×4 轮无新信，硬上限 6 秒）再触发，风暴攒成一批一次消费
- **教训**：阈值型闸门（"收齐 N 个"）天生会被迟到者重复满足——幂等是闸门的义务，不是可选项

---

## 元原则（按疗效排序）

1. **工具即教师**：工具层的拒绝/收拢错误信息，模型会在同一回合内自我纠正（实测两次）
2. **账本即登记处**：一切"去信箱里找 X"的指令都是 bug；一切以账本为准
3. **机器管协议，模型管语义**：收齐、裁决、投递、收尾、预算全是闸门的事；模型只写稿和审稿
4. **失败要被边界框住且有账可查**：产品承诺不是"不出错"，是"错了不失控"
5. **闸门必幂等，调度必去抖**：阈值会被迟到者重复满足，扇入会烧穿预算——规模化问题只在规模化时暴露，30 店是 5 店测不出的
